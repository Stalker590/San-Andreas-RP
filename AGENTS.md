## 3. Агентный цикл разработки (Anthropic & OpenAI Workflow)

При получении задачи на реализацию пункта из `ROADMAP.md` ты обязан выполнять работу строго по следующему 5-шаговому пайплайну:

### Шаг 1: Проверка зависимостей и контекста (Context Ingestion)
- Определи, к какой фазе `ROADMAP.md` относится задача.
- Проверь, какие публичные функции (`Module_Function`) из уже реализованных модулей (`core/`, `entities/`) должны использоваться в текущем файле, чтобы не дублировать логику.

### Шаг 2: Архитектурное пред-проектирование (Pre-Execution Scratchpad)
Перед генерацией кода кратко (3–5 буллетов) зафиксируй для себя и разработчика:
- Какие структуры `enum` и `static stock` массивы будут выделены в RAM.
- Какие граничные случаи (edge cases) и состояния гонки (race conditions) возможны (например: выход игрока во время асинхронного SQL-запроса, одновременное открытие одного багажника двумя игроками, переполнение стека Pawn).

### Шаг 3: Атомарная генерация кода
- Пиши код чисто, модульно, строго в рамках запрошенного файла.
- Соблюдай порядок секций внутри каждого `.pwn` файла:
  1. Заголовок файла и проверка защиты от повторного включения (`#if defined _mod_name_included`).
  2. Константы и макросы модуля.
  3. Перечисления (`enum`) и инкапсулированные массивы состояния (`static stock`).
  4. Внутренние (`stock` / `static`) вспомогательные функции.
  5. Публичный API модуля (`Module_ActionName`).
  6. Асинхронные SQL-колбеки (`forward OnModuleQuery...; public OnModuleQuery...`).
  7. Хуки системных колбеков (`hook OnGameModeInit`, `hook OnPlayerDisconnect`, `hook OnDialogResponse` и т.д.).
  8. Команды (`CMD:`) и таймеры (`ptask` / `task`).

### Шаг 4: Внутренний аудит перед выдачей (Self-Verification Checklist)
Перед завершением ответа прогони сгенерированный код через 7 проверок:
- [ ] Все ли строки пользовательского интерфейса (диалоги, сообщения в чат, HUD, 3D-тексты) написаны строго на грамотном английском языке (кодировка `Windows-1251`) без русских фрагментов в системных строках?
- [ ] Нет ли ни одного блокирующего `mysql_query` вне `OnGameModeInit`?
- [ ] Все ли строковые буферы в `mysql_format` используют спецификатор `%e` для пользовательского ввода?
- [ ] Освобождается ли `gStorageMutex` во всех ветках выхода (`return`) при работе со складами/инвентарем?
- [ ] Не используется ли тип `Float:` для денег, граммов или миллилитров?
- [ ] Передается ли `playerid` в асинхронные SQL-колбеки с проверкой `IsPlayerConnected(playerid)` и сверкой `account_id`/`char_id` (защита от подмены ID при быстром перезаходе другого игрока на тот же слот)?
- [ ] Скомпилируется ли код под `qawno` без единого `warning` (`tag mismatch`, `symbol is never used`, `number of arguments does not match definition`)?

### Шаг 5: Верификация, Автокоммит и Обновление прогресса
- Проверь, что код успешно компилируется через `pawncc` с флагами `-O2 -d1`.
- Если компиляция прошла успешно и код соответствует стандартам, **агент обязан самостоятельно выполнить через терминал следующие действия**:

## 4. Жесткие правила языка Pawn и `open.mp` v1.6.7+ (Anti-Hallucination)

Модели ИИ часто переносят привычки из C/C++, C# или устаревшего SA-MP 0.3.7. **Следующие правила обязательны к исполнению:**

### 4.1. Специфика компилятора Pawn (`qawno`)
- **Отсутствие динамической памяти:** В Pawn нет `malloc`, `new` (в стиле C++), `std::vector` или `List`. Все пулы данных выделяются статически на этапе компиляции с жесткими лимитами из `mod_config.pwn` и индексируются через `YSI\y_iterate` (`Iterator:Name<MAX_LIMIT>`).
- **32-битные знаковые ячейки (`cell`):** Стандартная ячейка Pawn — 32-битное знаковое целое от $-2\,147\,483\,648$ до $+2\,147\,483\,647$.
  * *Критично для БД:* Колонки MySQL типа `BIGINT UNSIGNED` (например, `storage_id` или крупные суммы в центах) при достижении значений $> 2.14 \times 10^9$ переполнят обычную переменную Pawn! Для крупных денежных балансов или длинных ID используй строковое представление (`cache_get_value_name`) либо храни капиталы в целых долларах (`USD`), а не в центах, если сумма может превысить $\$21\,000\,000$.
- **Строгая типизация тегов (Tag Strictness):** Никогда не смешивай теги `Float:`, `bool:`, `DBResult:`, `Cache:`, `Text3D:`, `PlayerText:` без явного приведения или правильного объявления переменной. Это главная причина `warning 213: tag mismatch`.
- **Операторы `switch`:** В Pawn внутри `switch` **нет сквозного проваливания (`fallthrough`)** как в C — каждый `case` автоматически завершается сам по себе (оператор `break` внутри `case` в Pawn вызывает ошибку компиляции!). Для нескольких значений используй перечень через запятую: `case 1, 2, 3:`.
- **Строки и массивы:** Всегда явно указывай `sizeof(buffer)` при работе с `format`, `mysql_format`, `strcat`, `strmid`. Никогда не захардкоживай длину массива в вызовах функций.

### 4.2. Стандарты экосистемы `open.mp` и библиотек
- **Только нативы `open.mp` v1.6.7+:** Используй актуальный синтаксис `open.mp` (например, `GetPlayerPoolSize()` не нужен при использовании `foreach (new i : Player)`).
- **Декомпозиция через `y_hooks`:**
  * Запрещено править глобальные колбеки в `main.pwn` ради логики конкретного модуля.
  * Используй `hook OnPlayerConnect(playerid)` внутри каждого модуля.
  * Всегда возвращай `return 1;` (или `Y_HOOKS_CONTINUE_RETURN_1`) в конце хука, чтобы не обрывать цепочку вызовов в других модулях (кроме случаев намеренного перехвата/блокировки, например, в `OnDialogResponse` или `OnPlayerCommandPerformed`).
- **Итераторы вместо циклов (`y_iterate`):**
  * Запрещено писать `for (new i = 0; i < MAX_PLAYERS; i++)`.
  * Всегда используй `foreach (new playerid : Player)` или кастомные итераторы пулов (`foreach (new s : StorageIter)`).
- **Процессор команд (`Pawn.CMD`):**
  * Используй синтаксис `CMD:commandname(playerid, params[])` и `alias:commandname("cmd1", "cmd2");`.
  * Для парсинга аргументов команд используй `sscanf` (если подключен) или строгую валидацию через встроенные функции Pawn.
</pawn_engineering_standards>

## 5. Стандарты работы с MySQL R41-4+ (`mod_database`)

1. **Кодировка соединения (`CP1251`):**
   * Сразу после `mysql_connect` в `mod_database.pwn` обязательно вызывается `mysql_set_charset(gMySQL, "cp1251");`, чтобы англоязычные названия предметов, рангов и организаций из таблиц `utf8mb4`, а также кириллица в сообщениях игроков корректно передавались в клиент GTA SA / open.mp без «кракозябр».
2. **Асинхронность по умолчанию:**
   * Любые `SELECT`, `INSERT`, `UPDATE`, `DELETE` во время игры выполняются **исключительно** через `mysql_tquery(gMySQL, query, "CallbackName", "d", playerid)`.
   * Использование блокирующего `mysql_query` разрешено **только** внутри `OnGameModeInit` (загрузка `item_definitions`, `craft_recipes`, `organizations`, `enterprises`, `properties`, `vehicles`).
3. **Защита от SQL-инъекций:**
   * Форматируй запросы исключительно через `mysql_format(gMySQL, query, sizeof(query), "...")`.
   * Любые строки, пришедшие от игрока (`rp_name`, `meta_str`, названия рангов/организаций, текст объявлений), обязаны экранироваться спецификатором **`%e`**, а не `%s`.
4. **Защита от Race Condition при входе/выходе (Generation Token):**
   * При отправке асинхронного запроса для `playerid` всегда передавай уникальный счетчик сессии слота `gPlayerSessionToken[playerid]`. В колбеке первым делом проверяй:
     ```pawn
     if (!IsPlayerConnected(playerid) || gPlayerSessionToken[playerid] != token) return 0;
     ```
   * Это на 100% исключает ситуацию, когда игрок вышел, на его ID зашел другой человек, и ему загрузились чужие данные из запоздавшего SQL-запроса.
5. **Атомарность критических транзакций:**
   * Перемещение предметов между хранилищами (`Storage_TransferItem`), покупка недвижимости/транспорта, создание персонажа и банковские переводы обязаны выполняться в единой транзакции (`START TRANSACTION; ... COMMIT;`) или с мгновенной записью в БД, а не через отложенный `Dirty-Flag`.
6. **Паттерн `Dirty-Flag` для фоновых данных:**
   * Периодические изменения (голод, жажда, пробег авто, износ, активные секунды онлайна для `Warrant Decay`) обновляются в RAM и помечают сущность флагом `is_dirty = true`. Фоновый таймер `Tick_Minute` сохраняет их пакетами без перегрузки БД.
</database_standards>

## 6. Ненарушимые игровые и архитектурные инварианты

При написании любой бизнес-логики ты обязан соблюдать следующие 9 законов мира **SAN ANDREAS RP**:

1. **Англоязычный интерфейс (English UI Mandate) и свобода общения в RP:**
   * Весь текст, который видит игрок в игре (заголовки и пункты `ShowPlayerDialog`, кнопки диалогов, `SendClientMessage`, `GameTextForPlayer`, `TextDraw` HUD, `3DTextLabel`, названия предметов `display_name`, названия ролей, рангов и фракций, а также интерфейс `/apanel` и `/ahelp`), обязан быть написан **исключительно на грамотном, естественном RP-английском языке** (в расчете на кодировку `Windows-1251`).
   * **Официальный рабочий язык** государственных организаций, правительства, судов, полиции, армии, СМИ и всех правовых процедур — **английский язык**.
   * При этом в проекте действует **свобода выбора языка общения в RP**: игрокам разрешено свободно общаться в IC/OOC-чатах на любом другом языке по собственному желанию. Запрещено вводить искусственные скриптовые ограничения, мут-фильтры или автобаны за использование иных языков в чате.
   * Запрещено смешивать английские и русские слова в системных UI-строках (неправильно: `"You placed M4 в Trunk"`, правильно: `"You placed the M4 assault rifle in the trunk"`). Исключение — только канонические аббревиатуры и модели (например, `M4`, `AK-47`, `USD`, `SSN`, `IBAN`, `LSPD`, `FBI`, `CIA`) и RP-ники игроков в формате `First_Last`.
2. **Целочисленная физика (Integer Physics):**
   * Масса всегда хранится и считается в **граммах (`INT`)** ($1\text{ кг} = 1000\text{ г}$).
   * Объем всегда хранится и считается в **миллилитрах (`INT`)** ($1\text{ л} = 1000\text{ мл}$).
   * Деньги всегда хранятся в **целых единицах валюты (`INT` / `BIGINT`)**. Использование `Float:` для расчетов денег, веса и объема запрещено.
3. **Закон сохранения материи и капитала (Zero-Faucet Economy):**
   * Ни один предмет, ресурс или доллар не должен создаваться функцией «из воздуха» (кроме первичной добычи на шахтах/вышках/лесопилках/фермах за счет труда игрока и стартового `Seed Money` Правительства).
   * Зарплата рабочему за добычу руды/нефти/леса выплачивается **строго из `reserve_usd` предприятия**. Если `reserve_usd < payout`, добыча возможна на склад, но денежная выплата блокируется с уведомлением об отсутствии средств в кассе предприятия.
4. **Универсальность `Storage` и защита от дюпа:**
   * Карманы (`PLAYER_LAYER1`, `PLAYER_LAYER2`), рюкзаки (`NESTED_BAG`), бардачки, багажники, сейфы фракций (`ORG_VAULT`), склады заводов (`ENTERPRISE_WAREHOUSE`), трупы (`CORPSE_LOOT`) и тайники (`WORLD_DROP`) управляются **только** через публичный API модуля `mod_storage.pwn`.
   * Любая мутация содержимого хранилища обязана захватывать мьютекс `gStorageMutex[slot_id]` и освобождать его перед выходом из функции.
   * Глубина вложенности контейнеров жестко ограничена: `MAX_NESTING_DEPTH = 2`.
5. **Двухслойная система инвентаря персонажа:**
   * При смерти (`HP <= 0.0`) содержимое `PLAYER_LAYER1` на 100% переносится в создаваемый контейнер трупа `CORPSE_LOOT`.
   * Содержимое `PLAYER_LAYER2` (документы, карты, телефон, надетый скин) **никогда** не выпадает при обычной смерти (PK) и может быть изъято только при аресте/ордере (`/search`) или при перманентной смерти (`CK`).
6. **Оружейная система без отдельных патронов:**
   * Отдельных предметов «патроны» не существует. Боезапас `ammo_count` хранится внутри экземпляра оружия в `storage_items`.
   * Каждый выстрел уменьшает `ammo_count` на 1 и пересчитывает общую массу предмета на величину `ammo_unit_weight_g`. При `ammo_count == 0` оружие **не удаляется** из инвентаря, а остается как пустой ствол (`0 M4`).
7. **Формула возраста персонажа:**
   * Возраст персонажа жестко вычисляется как $\text{Age} = 17 + \text{Level}$. Ручной ввод возраста запрещен.
8. **Честный `Warrant Decay`:**
   * Естественное снижение уровня розыска ($-1$ уровень за каждые $3600\text{ секунд}$ игры) тикает **только** при активной игре (проверка дельты последнего сетевого пакета игрока $< 15\,000\text{ мс}$). Время в AFK не засчитывается.
9. **Аудит критических операций:**
   * Каждое перемещение предмета между разными владельцами, передача наличных, банковский перевод, операция отмывания денег, изменение казны организации и выдача/снятие розыска обязаны вызывать `Audit_Log(...)`.
</domain_invariants>

## 7. Стандарты безопасности и античит-валидации

1. **Валидация диалогов (`OnDialogResponse`):**
   * Никогда не доверяй индексу `listitem`, пришедшему от клиента. При открытии диалога инвентаря, магазина или списка игроков сохраняй маппинг `gPlayerDialogSlotMap[playerid][listitem] = actual_db_or_pool_id` на сервере.
   * В `OnDialogResponse` повторно проверяй все предусловия (жив ли игрок, не в наручниках ли он, находится ли в радиусе $\le 3.5\text{ м}$ от багажника/склада/трупа, владеет ли он этим предметом прямо сейчас).
2. **Защита от флуда и спама запросами:**
   * Любые команды и действия, инициирующие SQL-запросы или тяжелые вычисления (крафт, взлом, открытие инвентаря, передача предметов), должны иметь серверный rate-limiter (кулдаун не менее `300-500 ms` через `GetTickCount()`).
3. **Серверный контроль состояния игрока:**
   * Здоровье (`HP`), броня (`Armour`), оружие в руках (`EquippedWeapon`) и координаты валидируются на стороне сервера. Прямое доверие клиентским значениям запрещено.
</security_rules>

## 8. Стандарты RBAC административной системы и аудита (Фаза 10)

Административная система строится на динамических ролях из `admin_roles` / `admin_role_permissions` и привязке `accounts.admin_role_id`. Следующие правила обязательны для любого кода, связанного с `/apanel`, `/ahelp`, `/sp` и админ-командами:

1. **Запрет хардкода уровней:**
   * Категорически запрещены проверки вида `admin_level >= X`, `admin_level == 100`, сравнение `admin_role_id` с числовыми константами или `IsPlayerAdmin` для игровой авторизации.
   * Единственный допустимый способ проверки — `Admin_HasPermission(playerid, E_ADMIN_PERM:perm)` с конкретным правом (например, `ADMIN_PERM_PLAYER_BAN`, `ADMIN_PERM_INV_GIVE_ITEM`).
   * Поле `accounts.admin_level` считается **legacy** и не должно влиять на доступ; его разрешено только читать для миграции/отображения.
2. **Обход только для Root:**
   * Безусловный доступ разрешен исключительно роли с `admin_roles.is_root == 1` и только внутри `Admin_HasPermission` (или `Admin_IsRoot`). Ветвление `if (Admin_IsRoot(playerid))` в бизнес-логике допустимо лишь как явное исключение, а не вместо проверки права.
   * Root-роль одна, создается сидом (`level = 100`, `is_root = 1`, `is_system = 1`) и не может быть удалена, переименована в другую системную роль или лишена флага через игровой UI.
3. **Управление ролями и защита от эскалации:**
   * Создание, изменение и удаление ролей — только `ADMIN_PERM_MANAGE_ROLES`; назначение и снятие администраторов — только `ADMIN_PERM_MANAGE_ADMINS`.
   * Роль не может выдать другой роли право, которым не обладает сама (кроме Root); нельзя снять последнего Root-администратора; нельзя назначить роль выше своего `level` (для не-Root).
4. **Обязательный аудит (`Core/Audit`):**
   * Каждое действие, изменяющее состояние (выдача/изъятие предметов, денег, транспорта, ключей, прав, баны, муты, варны, деморган, смена статов/навыков/лицензий/скина/фракции), обязано вызывать `Admin_Audit(...)` / `Audit_Log(...)`.
   * Запись должна содержать `admin_account_id`, `target_account_id` / `target_char_id`, `action_type`, параметры (сумма, `item_def_id`, количество, длительность) и результат. Отказ в доступе логируется как `ADMIN_DENIED`.
   * Запрещено выполнять привилегированную операцию «молча», даже если она инициирована Root-администратором.
5. **Валидация и асинхронность:**
   * Все ID, суммы, количества, `item_def_id`, координаты и индексы `listitem` из админ-диалогов повторно проверяются на сервере; для списков используется серверный маппинг, а не клиентский индекс.
   * Оффлайн-операции выполняются через `mysql_tquery` с проверкой `gPlayerSessionToken` и повторной валидацией цели; блокирующий `mysql_query` допустим только в `OnGameModeInit` при загрузке ролей.
6. **Кодировка и язык:**
   * Все строки админ-панели, `/ahelp`, HUD `/sp`, причин наказаний и объявлений — грамотный английский язык без русских фрагментов в системных сообщениях.
   * Официальный язык государственных организаций и правовых процедур — английский; при этом игроки сохраняют свободу общения в IC/OOC-чатах на любом языке.
   * Исходники `.pwn` с кириллицей (комментарии, сообщения игроков) сохраняются в `Windows-1251 (CP1251)`; соединение MySQL обязано использовать `mysql_set_charset(gMySQL, "cp1251")`.
7. **Модульная дисциплина:**
   * RBAC-ядро и проверки живут в `systems/mod_admin.pwn`; UI-диалоги и HUD — в `ui/mod_admin_panel.pwn`. UI не изменяет состояние мира напрямую, а вызывает публичный API `Admin_*` и профильные модули (`Storage_*`, `Char_*`, `Org_*`, `Vehicle_*`).
</admin_rbac_standards>

## 9. Соглашения об именовании и оформлении кода

Для единообразия всей кодовой базы придерживайся строгой нотации (код и SQL — строго на английском, UI-строки — строго на английском; русские комментарии и сообщения игроков в чате допускаются):

- **Константы и макросы:** `UPPER_SNAKE_CASE` (пример: `MAX_ACTIVE_STORAGES`, `KG_TO_GRAMS(%0)`).
- **Перечисления (`enum`):** Префикс `E_` в `UPPER_SNAKE_CASE` (пример: `enum E_STORAGE_DATA { ... }`).
- **Глобальные массивы/переменные (только в `mod_config.pwn`):** Префикс `g` в `PascalCase` (пример: `gMySQL`, `gPlayerSessionToken`).
- **Инкапсулированные массивы модуля:** Объявляются как `static stock` с префиксом `s` (пример: `static stock sStoragePool[MAX_ACTIVE_STORAGES][E_STORAGE_DATA];`).
- **Публичные функции модуля (API):** `ModulePrefix_FunctionName` в `PascalCase` (пример: `Storage_TransferItem`, `Skills_Add`, `Org_HasPermission`).
- **Внутренние функции модуля:** `static stock Internal_FunctionName` в `PascalCase`.
- **SQL-колбеки:** `forward OnModule_ActionName(...); public OnModule_ActionName(...)`.
- **Отступы и скобки:** 4 пробела (без табуляции), фигурные скобки в стиле Allman (каждая скобка на новой строке) для структур и функций.
</code_style>
